# Getting started

This guide is the happy path for a **Vite + React 19** app: install from npm, import CSS, wrap providers, and render a Button.

## Install

```bash
pnpm add @var-ui/react @var-ui/core @var-ui/icons react react-dom react-aria-components
```

```bash
npm install @var-ui/react @var-ui/core @var-ui/icons react react-dom react-aria-components
```

`@var-ui/icons` is optional. Without it, pass `icons={{}}` to `IconProvider`.

You do not add `typestyles` to the app. It arrives with `@var-ui/core`.

## Import CSS

```ts
import '@var-ui/core/styles.css';
```

That file includes every recipe, base HTML styles, and the default theme. Custom `createDesignTheme` modules and unused-recipe shedding use extract instead — see [Installation](/docs/installation).

## Providers

Mount `DesignSystemProvider` with `applyToDocument` and `IconProvider` at the root:

```tsx
import { defaultIcons } from '@var-ui/icons';
import { DesignSystemProvider, IconProvider } from '@var-ui/react';

<DesignSystemProvider applyToDocument>
  <IconProvider icons={defaultIcons}>{children}</IconProvider>
</DesignSystemProvider>;
```

Without `@var-ui/icons`, pass `icons={{}}` to `IconProvider`.

`applyToDocument` puts the theme class on `html`, so the theme reaches every element, including dialogs and popovers.

## First component

```tsx
import { Button } from '@var-ui/react';

<Button>Click me</Button>;
```

## Astro without React

```bash
pnpm add @var-ui/astro @var-ui/core
```

Import the same stylesheet in a layout, then import Astro components:

```astro
---
import '@var-ui/core/styles.css';
import { Button } from '@var-ui/astro';
---

<Button>Click me</Button>
```

See `examples/astro-app` in the repo for a full **workspace** tree. That example still extracts CSS with the TypeStyles Vite plugin because it lives in this monorepo.

## Direction and overlays

### Direction and locale

Pass `direction` and a real `locale` on `DesignSystemProvider`:

```tsx
<DesignSystemProvider applyToDocument direction="rtl" locale="he-IL">
  {children}
</DesignSystemProvider>
```

`applyToDocument` syncs `html dir` (and `lang` when `locale` is set) after hydration / on mount. It always writes `dir` for the resolved direction — including default `ltr`. If SSR set `<html dir="rtl">` and the client provider omits `direction`/`locale`, mount will rewrite `dir` to `ltr`. SSR apps that care about first paint should set `<html dir>` (and `lang` if needed) themselves **and** pass matching `direction`/`locale` to the provider.

Anchored popups (`Popover`, `Menu`, `Tooltip`, and the field popups) place `start` and `end` with CSS logical values. They follow the document `dir` that `direction` writes — `applyToDocument` sets it on `html`. `locale` formats dates and numbers and configures React Aria; it does not choose the popup side. `I18nProvider` only accepts `locale`.

- Prefer a real RTL locale (`he-IL`, `ar-EG`) with `direction="rtl"` so formatting and popup sides agree.
- `direction="rtl"` with no locale wraps `I18nProvider` with `ar` so React Aria formatting matches the direction. That fallback does **not** set `html lang="ar"`. Popup sides still follow `dir`.
- `direction="ltr"` (explicit) with no locale wraps `I18nProvider` with `en-US` so a nested LTR island does not inherit a parent RTL locale.
- `locale="en-US"` plus `direction="rtl"` keeps English formatting. Popup `start` / `end` still follow `dir`.
- If you omit `direction` but pass `locale`, `dir` is derived from RAC `isRTL(locale)`, and popups follow that `dir`.
- `useDirection()` returns `{ direction, isRtl }` and defaults to `ltr` when no provider is mounted.
- Directional icons opt in: `<Icon name="chevronRight" data-mirror={isRtl || undefined} />`.

Do not set `dir` on the whole docs site to try this — use a `DirectionProvider` island (see Hidden).

### Overlays and stacking

Dialogs, drawers, popovers, menus, tooltips and toasts are native `<dialog>` and `[popover]` elements in the browser top layer. They need no portal, no provider and no `z-index`, and they always paint above the page. The top layer orders overlays by when they opened, so the most recently opened one is on top.

Because they render in place, a theme class on any ancestor reaches them, and CSS custom properties inherit as usual. There is no `portalContainer` to set. The flip side is that a `<button>` inside a dialog inside a `<form>` submits that form (give it `type="button"`), and DOM events bubble through the dialog's real ancestors; see [Plain CSS](/theming/plain-css).

How overlays open and close, their state attributes, and the `onOpenChange` reasons are documented in [Overlay lifecycle](/docs/overlay-lifecycle).
